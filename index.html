      BrightCart / After “Place order”Concept 1 of 3 · Delivery guarantees

      Delivery guarantees: when does the worker say “done”?

      1 · TakeA worker takes Emma’s receipt job. The queue hides it from other workers and starts a timer: the visibility timeout.
      →
      2 · WorkThe worker calls the email provider and sends the receipt.
      →
      3 · ACKThe worker tells the queue “done”. The queue deletes the job.
      No ACK before the timer runs out? The job becomes visible again and another worker takes it.

      At-most-once

      ACK → work

      A crash during the work: the job is already deleted. Lost.

      Never twice. Maybe never.

      Fine for view counters, analytics pings.

      At-least-once

      work → ACK

      A crash before the ACK: the job comes back. Runs again.

      Never lost. Maybe twice.

      The default: SQS, Celery acks_late, Kafka commit-after-processing.

      Effectively-once

      work → ACK + dedup

      It still runs twice, but the second run changes nothing.

      Exactly-once delivery over a network is not possible. Exactly-once effect is.

      Needs an idempotency key: concept 2.

      Repeats will happen. The question is not “will it repeat?” but “what happens when it does?”

      Retry types: when do you try again?

      Six workers fail at the same moment because the email provider is down. Each dot is one retry.

      Retry only what can succeed

      Timeouts, 503, 429: retry. “Card declined”, bad address: fail fast.

      After N attempts the job goes to a dead-letter queue, where someone looks at it.

      Backoff alone is not a limit. Share one rate limit across all workers.

      Sync, await, polling, webhook: who waits, and who calls whom?

      Sync call

      const r = charge()
      Who waits
      Your thread, doing nothing
      Answer arrives
      On the same open connection
      Used for
      Card authorisation at a till, login, reading one DB row

      async / await · callback

      const r = await charge()
      Who waits
      Nobody: the thread serves other requests
      Answer arrives
      Same connection; your code resumes
      Used for
      Node, Python asyncio, Go: every HTTP and DB call

      Polling

      GET /payments/7
      Who waits
      You, by asking again and again
      Answer arrives
      On one of your many requests
      Used for
      Job-status APIs, report exports, a backstop when webhooks fail

      Webhook

      POST /webhooks/payment
      Who waits
      Nobody. The provider calls you
      Answer arrives
      On a new request, to your URL
      Used for
      Stripe / Razorpay payment status, GitHub push, Twilio SMS delivery
      await and callbacks keep your code from blocking while one call is in flight. Polling and webhooks are how you learn a result that arrives after the call is over. A webhook is a callback across the network.

      Receiving a webhook: five rules, and what breaks without each

      1 · Verify the signatureAnyone can POST to your URL. A forged “paid” ships Emma’s order for free.Check the HMAC signature header (e.g. Stripe-Signature) with your secret. Reject with 401.
      2 · Reply 2xx fast, work laterA slow handler misses the provider’s timeout. It retries, and now you process it twice.Store the event, enqueue a job, return 200 within a second.

      BrightCart / After “Place order”Theory · Step 4

      Dedup: duplicates get in at three doors

      At-least-once means every door can let the same action through twice. Each door needs a key that names the business action.

      Door 1 · the API

      Emma double-taps “Place order”

      Two requests, two orders, two charges.

      Client sends an Idempotency-Key header. Store the key with the response; a repeat gets the stored response.
      →
      Door 2 · the consumer

      The queue delivers the job again

      No ACK, timeout, redelivery: normal at-least-once.

      Inbox table with a unique message_id, written in the same transaction as the database change.
      →
      Door 3 · the provider

      The call timed out after it worked

      You cannot know whether the charge or email happened.

      Send the same key to the provider (Stripe’s API takes an Idempotency-Key header), or check its status before retrying.
      Key the action (order:7:receipt), not the attempt (job-run-42), and keep keys longer than your longest retry window.
      BrightCart / After “Place order”Theory · Step 4 recap

      The retry and dedup toolkit

      Every production queue consumer ends up with the same six tools.

      Retry with backoff + jitter

      Exponential delays with a random spread, so 10,000 jobs do not retry in the same second. Bound the attempts.

      Classify errors

      Timeouts and 503s: retry. Validation errors and “card declined”: do not retry; fail fast and say why.

      Dead-letter queue

      After N attempts, park the job. Alert, inspect, fix, redrive. A DLQ nobody watches is data loss.

      Idempotency key

      One key per business action (order:7:receipt), unique in the same transaction as the effect, or sent to the provider.

      Outbox

      Save the order and the job row in one transaction; a relay publishes it. No “saved but never published”.

      Leases and limits

      Visibility timeout longer than the job, or a heartbeat. Cap concurrency at what the provider allows.

      BrightCart / After “Place order”Theory · Step 6

      The saga pattern: two ways to run it

      A saga splits one long business transaction into local transactions, each paired with a compensating action that undoes it. If step 3 fails, run the compensations for steps 2 and 1. (Garcia-Molina and Salem, 1987)

      Choreography · step 6Orchestration · step 7

      Where the flow livesSpread across the consumersIn one place: the workflow code

      BrightCart / After “Place order”Theory · Step 6

      Kafka, RabbitMQ and the consumers: what each brings

      Kafka · a log

      • Events are appended and kept for a retention period, not deleted on read
      • Order is kept per partition: key events by order_id
      • Many consumer groups read the same events; a new one can replay history

      RabbitMQ · a broker

      • Exchanges route each message to queues
      • A message is gone once acked
      • Per-message acks, retries and dead-letter exchanges

      Any runtime

      • A service you run: pods in a consumer group, scaled on lag
      • Or a cloud function the provider runs: AWS Lambda, Google Cloud Run functions, Azure Functions
      • Same rules everywhere: idempotent handler, a dead-letter destination

      What choreography resolves

      • Teams ship independently
      • Add a consumer without touching checkout
      • Each service scales on its own
      • Kafka keeps history for replay and audit

      What it costs

      • No single view of order #7
      • Compensations spread across teams; chains can loop or stall silently
      • Needs an outbox, idempotent consumers and a correlation ID
      • Eventually consistent: Emma may see “placed”, then “cancelled”
      BrightCart / After “Place order”Temporal · Workflow & Activity

      Workflow decides. Activities do the work.

      One order, two responsibilities. Follow Emma’s order #7.

      Workflow — coordinates the order

      • Chooses the next step; waits for payment or a deadline.
      • Deadline? Checks payment state before releasing stock or refunding.
      • Fulfilment fails? Calls refundPayment().

      Activity — performs one task

      • Reserves stock, charges payment, fulfils or sends email.
      • Calls a database or an external service.
      • May retry; use idempotency to make repeats safe.

      BrightCart / After “Place order”Webhooks · Authentication & safe processing

      Can BrightCart trust this payment callback?

      Razorpay signs each payload with a shared webhook secret, so BrightCart can verify who sent it.

      Signature verification

      POST /webhooks/razorpay
X-Razorpay-Signature: <signature>

Exact raw request bytes
{ "event": "payment.captured",
  "payload": { ... } }

      HMAC-SHA256(secret, raw_body)

      Verify with the provider utility before processing. Parsing and reserializing the body can break the signature.

      The signing secret stays on the servers.

      From trusted request to safe action

      1. Authenticate the payloadVerify X-Razorpay-Signature. Reject an invalid signature.
      2. Validate the business factsMatch the stored order, payment, expected amount and currency.
      3. Record receipt durablyDeduplicate x-razorpay-event-id. Return success after saving.
      4. Process safely on every retrySignal the Workflow asynchronously. Guard its state transition so repeats cannot fulfil twice.
      Late or out of order? Preserve the final state and reconcile unclear payments. If a paid order’s stock hold expired, apply the release/refund policy explicitly.
      A valid signature authenticates the payload. Stored order state determines the allowed action.

      Temporal · orchestration

      The flow is one Workflow function. Each step is an Activity.

      async function processOrder(order) {      // Workflow
  await reserveStock(order)               // Activity
  await chargePayment(order)              // Activity
  const paid = await condition(() => gotPaid, '10 min')
                                       // Signal or Timer
  if (!paid) return await releaseStock(order)
  try { await fulfilOrder(order) }        // Activity
  catch { await refundPayment(order); await releaseStock(order) }
  await sendReceipt(order)                // Activity
}

      One owner. “Where is it?” = read Workflow order-7’s Event History.

      1 · RemembersEvery step of order-7 is written to its Event History, in the Service.
      2 · DecidesA Workflow Task runs your code to pick the next step. The code is the process.
      3 · DispatchesEach step becomes an Activity Task on a Task Queue. Any Worker can take it.
      4 · WaitsTimers and Signals live in the Service. A 10-minute wait holds no thread.
      5 · RecoversRetries Activities; a new Worker replays the history and carries on.
      Kafka moves facts between teams. Temporal runs a process. Many systems use both: an Activity can publish OrderCompleted to Kafka.

        Temporal beyond orders: AI agents, and more

        An AI agent is a long-running, multi-step process that calls slow, flaky, expensive and non-deterministic services. That is the shape Temporal was built for.

        Workflow · research-agent
        1LLM call: make a planActivity · retried on rate limits and timeouts
        2Tool calls: search, SQL, internal APIsActivities
        3Wait for a human to approveSignal · can wait for days, no worker held
        4LLM call: write the answerActivity
        ↺ loop back to 1 until the task is done

        Why it fits

        • A crash resumes at the same step; finished LLM calls are not repeated, so no tokens are paid twice
        • Model output differs on every call, so it is recorded once and replayed as-is
        • Retries with backoff absorb rate limits
        • Human-in-the-loop waits cost nothing while waiting
        • The history is a full trace of every prompt and tool call

        Temporal’s official OpenAI Agents SDK integration runs the agent loop as a workflow and each model call as an activity.
